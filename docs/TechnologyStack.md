# Технологический стек Coffee House

## 1. Назначение документа

Документ фиксирует технологии, которые планируется использовать для реализации Coffee House Landing Page.

Выбранный стек должен:

- соответствовать требованиям RS School Landing Page;
- обеспечивать две страницы, адаптивность и две цветовые темы;
- позволять самостоятельно реализовать всю проверяемую интерактивность;
- оставаться простым для сопровождения;
- не добавлять зависимости без практической необходимости.

Фактически установленными считаются только технологии, подтверждённые конфигурацией и lock-файлом проекта. Этот документ не является разрешением автоматически устанавливать зависимости.

## 2. Основной runtime-стек

| Технология | Назначение | Решение |
| --- | --- | --- |
| HTML5 | Семантическая структура Home и Menu | Использовать |
| CSS3 | Визуальное оформление, темы и адаптивность | Использовать |
| JavaScript ES Modules | Данные, DOM и интерактивность | Использовать |
| JSON | Данные карточек Coffee, Tea и Dessert | Использовать |
| Browser Web APIs | DOM, события, хранение темы и адаптивное поведение | Использовать |

В production-код не входят JavaScript- и CSS-фреймворки.

## 3. HTML

Используем:

- семантические элементы `header`, `nav`, `main`, `section`, `footer`;
- нативные `button` и `a` для интерактивных действий;
- корректную иерархию заголовков;
- `picture`, `source` и `img` для адаптивных изображений при необходимости;
- нативные атрибуты доступности и ARIA только там, где HTML-семантики недостаточно;
- отдельные документы для Home и Menu.

Не используем:

- HTML, сгенерированный только ради повторения статической разметки карточек;
- `div` вместо кнопок и ссылок;
- скриншоты макета вместо настоящей разметки.

## 4. CSS

Используем обычный CSS без препроцессора.

Основные возможности:

- CSS custom properties для дизайн-токенов и цветовых тем;
- Flexbox и CSS Grid;
- media queries;
- `clamp()` для контролируемой адаптивной типографики и размеров, где это соответствует макету;
- псевдоклассы `hover`, `active`, `focus-visible`;
- `prefers-reduced-motion` для необязательных анимаций;
- логические свойства CSS, если они делают стили понятнее;
- классы состояний и `data-*` атрибуты для связи с JavaScript.

Для темы предпочтительны CSS custom properties на корневом элементе:

```css
:root,
[data-theme='light'] {
  /* Light theme tokens */
}

[data-theme='dark'] {
  /* Dark theme tokens */
}
```

Не используем:

- Bootstrap, Tailwind CSS и другие CSS-фреймворки;
- CSS-in-JS;
- Sass/SCSS без отдельной необходимости;
- `!important` как системный способ управления специфичностью.

## 5. JavaScript

Используем современный JavaScript и ES-модули.

Планируемые модули:

- `theme` — переключение и восстановление темы;
- `burger` — мобильная навигация;
- `slider` — Favorites Coffee;
- `menu` — загрузка данных, категории и рендер карточек;
- `modal` — выбранная позиция, параметры и цена;
- небольшие общие DOM-утилиты только при реальном повторном использовании.

Принципы:

- данные отделены от DOM-рендеринга;
- карточка и modal используют один объект данных;
- модули не создают неявных глобальных переменных;
- обработчики событий устанавливаются один раз;
- состояние хранится в минимальном объёме;
- публичные функции модулей имеют одну понятную ответственность;
- расчёт цены отделён от визуального отображения.

Не используем:

- TypeScript;
- React, Vue, Angular, Svelte и другие фреймворки;
- jQuery;
- библиотеки slider, modal, burger menu и готовые UI-компоненты;
- минифицированный или обфусцированный исходный код.

## 6. Browser Web APIs

| API | Назначение |
| --- | --- |
| DOM API | Создание карточек, управление состояниями и атрибутами |
| Event API | Клики, клавиатура, изменение размеров и интерактивность |
| `localStorage` | Сохранение выбранной темы |
| `matchMedia` | Проверка media queries из JavaScript при необходимости |
| Pointer Events | Унифицированное управление мышью и сенсорным вводом |
| History/Location | Переходы между страницами и якорями средствами браузера |

`ResizeObserver` допускается только при необходимости наблюдать конкретный контейнер. Для обычной адаптивности приоритет имеют CSS и `matchMedia`.

## 7. Данные

Источник каталога — официальный `products.json` из задания RS School.

Требования:

- файл хранится отдельно от UI-кода;
- данные Coffee, Tea и Dessert не дублируются в HTML;
- карточки и modal строятся из одного набора объектов;
- базовая цена и параметры используются для детерминированного расчёта;
- данные не изменяются напрямую во время рендера;
- ошибки загрузки не скрываются и имеют понятное поведение интерфейса.

Backend и база данных не требуются.

## 8. Хранение состояния

В `localStorage` сохраняется только выбранная тема.

Состояния burger, slider, категории, дополнительных карточек и modal являются состоянием текущего интерфейса и по умолчанию не сохраняются между перезагрузками.

Не сохраняем:

- персональные данные;
- секреты;
- выбранные добавки без требования задания;
- полные копии каталога.

## 9. Графические ресурсы

| Формат | Использование |
| --- | --- |
| SVG | Логотип, интерфейсные и социальные иконки |
| WebP | Основной формат растровых фотографий, если качество экспорта соответствует макету |
| PNG | Изображения с прозрачностью, когда SVG или WebP не подходят |
| JPEG | Фотографии, если это исходный или более подходящий формат |
| WOFF2 | Локальные web-шрифты |

PDF используется только как источник макета и ресурсов. PDF и скриншоты не встраиваются вместо HTML/CSS-секций.

При конвертации сохраняются исходные файлы, пропорции, качество и корректное кадрирование.

## 10. Планируемая среда разработки

Следующие инструменты планируется подключить после отдельного подтверждения установки зависимостей:

| Инструмент | Назначение |
| --- | --- |
| Node.js LTS | Среда выполнения инструментов разработки |
| npm | Управление dev-зависимостями и командами проекта |
| Vite | Локальный сервер и production-сборка |
| ESLint | Статическая проверка JavaScript |
| Prettier | Единое форматирование HTML, CSS, JavaScript, JSON и Markdown |
| Vitest | Unit-тесты чистой логики |
| jsdom | DOM-тесты модулей без полноценного браузера |
| Playwright | Критические E2E-сценарии и визуальная проверка размеров экрана |

Точные версии фиксируются в `package.json` и `package-lock.json` при инициализации. Перед установкой необходимо проверить актуальные совместимые версии.

### Почему Vite

- поддерживает ES-модули;
- не требует фреймворка;
- предоставляет удобный локальный сервер;
- поддерживает две HTML-страницы;
- создаёт production-сборку;
- позволяет включить source maps, как требует задание при использовании сборщика.

Если пользователь решит не использовать сборщик, проект может работать как статический HTML/CSS/JavaScript. В этом случае команды и структура должны быть пересмотрены до начала реализации.

## 11. Тестирование и контроль качества

### Unit-тесты

Vitest используется для чистой логики:

- расчёт итоговой цены;
- выбор данных категории;
- ограничение количества карточек;
- переход индекса slider по кругу;
- преобразование состояния темы.

### DOM-тесты

Vitest с jsdom используется для ключевых модулей:

- переключатель темы;
- категории меню;
- открытие и закрытие modal;
- синхронизация ARIA-состояний.

### E2E и визуальная проверка

Playwright используется для критических сценариев:

- Home ↔ Menu;
- burger menu;
- slider;
- Coffee, Tea и Dessert;
- дополнительные карточки;
- modal и пересчёт цены;
- сохранение темы после перезагрузки;
- ширины 1440, 768 и 380 px.

Количество тестов должно быть пропорционально риску. Тесты не изменяются только ради получения успешного результата.

## 12. Валидация и браузерная диагностика

Используем:

- HTML Validator для разметки;
- Chrome DevTools для Console, Network, DOM и CSS;
- Lighthouse как дополнительную диагностику доступности и производительности;
- ручное сравнение с Figma и локальными PDF;
- проверку клавиатурной навигации;
- проверку `prefers-reduced-motion`;
- проверку отсутствия горизонтальной прокрутки.

Lighthouse не заменяет функциональные и визуальные проверки.

| --- | --- |

## 14. Команды проекта

После инициализации предполагаются команды:

```text
npm run dev
npm run lint
npm run format:check
npm run test
npm run test:e2e
npm run build
npm run preview
```

Фактические команды определяются `package.json`. До его создания эти команды считаются планом, а не доступным интерфейсом проекта.

## 16. Условия изменения стека

Изменение принятого стека допускается, если:

1. этого требует актуальная версия задания;
2. существующая технология не покрывает обязательное требование;
3. изменение согласовано с пользователем;
4. обновлены это описание, ТЗ и конфигурация проекта;
5. выполнены релевантные проверки после изменения.

Новая зависимость не добавляется только ради сокращения небольшого объёма кода, который можно ясно и безопасно реализовать средствами платформы.
